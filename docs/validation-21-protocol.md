# 第二轮验证预设方案

用户已确认：21 个独立案例 × 3 次重复 × 5 组对照。此次只验证已实现的按需执行、跨轮次去重与等待、工具复用、选择性记忆，不增加新的优化机制。

执行状态（2026-09-20 补充）：315/315 组已完成，审计通过。结果见 [validation-21-results.md](validation-21-results.md)。以下预设规则保持原样。

## 固定设置

- 从冻结测试集的七类场景分别取编号 000、001、002，共 21 个案例；与第一轮开发集 pilot 的案例 ID 不重叠。
- 每例 6 个事件；每例重复 3 次、运行 B0/B1/B2/B3/M-Full，共 315 组案例运行、1,890 个事件。
- DeepSeek `deepseek-flash`，temperature=0，thinking_mode=disabled，max_output_tokens=1200。
- 仅 warm 缓存；每组每例每次重复独立初始化状态、记忆和缓存，热缓存只在案例内跨事件保留。
- 规则、提示词、记忆策略和评价标准保持不变；实际源代码与数据集快照保存到本轮运行目录。
- 按既有 runner 的固定种子交错运行组别。重复请求、网络失败、重试、质量失败均保留，不剔除不利样本。
- 请求硬上限 4,500、Token 预算计量上限 9,000,000；为第一轮 pilot 上限的 9 倍，不是预期用量。按第一轮简单外推约 2,000 次请求、约 100 万 Token，实际由新案例和重试决定。
- 配置文件：`configs/deepseek-validation-21.json`。

## 核对指标

1. B0→B1：请求数、必要分支覆盖、重复干预、任务成功率。
2. B1→B2：后端读取、缓存命中、任务质量与耗时；不因未达 50% 目标修改场景。
3. B2→B3：历史约束案例表现、原始输出约束遵守、调用和 Token 的成本变化。
4. M-Full→B3：输入 Token、案例成功率与约束检查。
5. B0→B3：总体执行开销和案例 P50/P95，仅代表合成环境。

统计独立单位为 21 个案例；63 次重复运行不是 63 个独立案例。按案例聚类 Bootstrap 保留三次重复，报告分子分母、分场景结果和 95% CI。记忆类仍只有 3 个独立案例，避免泛化为所有任务。

原始 JSONL、SQLite 状态、供应商 usage、manifest、代码快照和 report 均保存；结束后补充本轮结果解读，第一轮 pilot 结果不覆盖、不合并冒充同一数据集。
